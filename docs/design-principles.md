# journal.stdy.blog 디자인 원칙

> 상태: 2026-08-05 외부 출처를 이 리포의 결정과 통합한 파생 UI 해석.
> 구현 계약은 [`spec-first-slice.md`](./spec-first-slice.md), 순서는
> [`ui-improvement-plan.md`](./ui-improvement-plan.md), 제품 판단은
> [`charness-artifacts/ideation/2026-07-26-concept-ideation.md`](../charness-artifacts/ideation/2026-07-26-concept-ideation.md)에 둔다.
> 이 문서는 `AGENTS.md`·아이데이션·구현 계약보다 높은 권위를 갖지 않는다.

## 한 문장

journal.stdy.blog의 UI는 고정된 화면을 꾸미는 일이 아니라, **사용자가 쓴 글자를
잃지 않으면서 작성 의도와 사용자의 선호와 현재 맥락을 조합해 기록·에너지·인출을
가능하게 하는 오프라인 우선 표면**이다.

```text
design outcome = f(design intent, user preference, context)
```

여기서 디자인 런타임은 새 프레임워크를 도입한다는 뜻이 아니다. 시맨틱 HTML,
논리적 CSS, CSS 변수, 현재의 Svelte 표면, 정적 검사, 실제 브라우저 검증으로 같은
의도를 여러 맥락에서 실현한다. 광학적 미세 조정과 기록의 의미·우선순위 판단은 사람의
몫으로 남긴다.

## 원칙

### 1. 좌표보다 의도를 선언한다

픽셀 위치를 고정하는 대신 무엇을 보장하려는지 표현한다.

- 본문 입력은 고정 폭이 아니라 읽고 쓰기 좋은 글줄 길이와 화면 여백의 관계로 설계한다.
  구현 후보는 `max-inline-size`, `ch`, `clamp()`와 논리적 여백이다.
- 입력·버튼·그래프·배너의 크기와 간격은 임의의 숫자 묶음이 아니라 읽기·조작·상태
  전달이라는 역할로 설명한다.
- 화면 방향, 언어 방향, 글자 크기, 컨테이너 폭이 바뀌어도 같은 의도가 유지되는지
  먼저 본다.

### 2. 기능 수보다 조합 가능한 가능성을 최적화한다

이 앱의 목적은 복붙을 없애고 에너지 레벨을 다시 읽게 하는 것이다. 날짜 이동, 텍스트
블록, 에너지 점수·이유, 그래프, import/export, 수동 push라는 원시 요소가 여러 사용
경로를 만들게 한다.

- 새 UI를 제안할 때 먼저 “사용자가 새로 할 수 있는 일”을 적고, 기존 요소의 조합으로
  만들 수 있는지 확인한다.
- 폴더·태그·새 분류 축·새 설정 모드를 UI에 추가하지 않는다. 기록의 구조와 인출의
  구조가 갈라지면 사용자가 같은 일을 두 수단으로 배워야 한다.
- 그래프는 에너지를 다시 읽는 통로이지, 별도 데이터 입력 체계나 새 날짜 선택기가 아니다.

### 3. 맥락을 입력으로 취급하고 우아하게 망가진다

대상은 이상적인 데스크톱 하나가 아니다. 적어도 다음 맥락을 함께 본다.

- 좁고 넓은 화면, 세로·가로 방향, 한국어와 긴 영문·URL
- 마우스·터치·키보드·스크린 리더, 큰 글씨와 브라우저 확대
- 오프라인·느린 네트워크·동기화 실패. 오프라인 보장은 서비스워커가 설치·활성화된
  뒤의 warm-cache를 뜻하며, 최초 방문 cold offline launch는 현재 보장하지 않는다.
- `prefers-reduced-motion`, forced colors/high contrast, 저시력·색각 차이

네트워크가 없거나 동기화가 실패해도 로컬 기록·날짜 이동·그래프·export 같은 핵심
작업은 살아 있어야 한다. 현재 앱은 Svelte SPA이므로 JavaScript 실행이 전제이고
SSR/no-JS fallback은 이 계약에 포함하지 않는다. 동기화는 자동화하지 않으며,
미동기화·분기·저장 오류는 숨기지 않는다.

### 4. 접근성은 별도 장식이 아니라 사용성의 기본값이다

- 시맨틱 HTML, 이름 있는 영역, 논리적인 키보드 순서, 명확한 포커스, 충분한 터치
  표면을 기본 계약으로 삼는다.
- 색상 하나에 점수·경고·동기화 상태의 의미를 맡기지 않고 텍스트·구조·상태를 함께
  제공한다. 그래프도 색만으로 차원을 구분하지 않는다.
- 큰 글씨·확대·모션 줄임·forced colors에서 입력과 인출이 계속 가능한지 검사한다.
- 자동 검사 통과를 접근성 완성으로 오해하지 않는다. 실제 브라우저와 실제 읽기·쓰기
  흐름에서 사용자가 과업을 끝내는지 사람이 확인한다.

### 5. CSS의 교차 관심사는 범위와 상호작용을 드러낸다

CSS selector는 pointcut처럼, cascade는 weaving처럼 작동한다. 전역 스타일의 영향은
정상일 수 있지만 예외 override가 많아지는 것은 설계나 범위가 잘못됐다는 신호다.

- 전역 규칙은 reset·토큰·본문 기반으로 최소화하고, 컴포넌트 규칙은 소유 경계를
  드러낸다.
- `@layer`, 논리적 속성, 역할 기반 토큰, 좁은 selector와 `:where()`는 실제 경계를
  단순하게 만들 때만 사용한다.
- 타이포그래피·색·반응형·접근성·상태 스타일이 서로 간섭할 수 있음을 전제로,
  “좁은 화면+큰 글씨+포커스”, “오프라인+경고”, “모션 줄임+그래프” 같은 조합을
  회귀 검증한다.
- 특정 한 곳을 살리기 위한 무작위 override를 쌓지 않는다. 반복되는 예외는 원래
  aspect의 범위를 고친다.

### 6. 취향은 제약 안에서 보존하고 AI에는 판정 가능한 일을 맡긴다

차분한 단일 기록 표면과 짧은 기능 목록은 이 앱의 취향이다. 일반적인 대시보드,
생성형 장식, 앱 안의 LLM으로 평탄화하지 않는다.

- 색 대비·overflow·시맨틱 구조·렌더 결과처럼 판정 기준이 명확한 일은 검사와 테스트로
  강제한다.
- AI에게 문장을 대신 쓰게 하거나 에너지 이유를 자동 생성하게 하지 않는다. 사람이
  외재화할 글자와 의미를 결정한다.
- 시각적 최종 판단, 기록의 맥락, 무엇을 버릴지는 사람이 맡는다.

### 7. 저장보다 인출을 우선하고, 기록의 맥락을 보존한다

저널 UI는 입력 칸을 많이 보여주는 것이 목적이 아니라, 쓴 내용을 나중에 다시 읽고
에너지 변화를 알아차리게 하는 것이 목적이다.

- 날짜 이동·전날의 오늘·그래프·export는 새 분류 기능이 아니라 같은 기록의 인출 경로다.
- 점수만 크게 강조해 이유를 잃게 하지 않는다. 수치와 이유가 함께 읽혀야 에너지 추적이
  기록 행위와 분리되지 않는다.
- 충돌·분기·저장 오류는 사용자 글자를 보존했다는 사실과 다음 행동을 함께 보여준다.
  자동 병합·자동 삭제·자동 문장 생성으로 판단을 대신하지 않는다.

### 8. 모든 디자인 주장은 실행 가능한 증거를 가진다

“더 예뻐졌다”는 완료 기준이 아니다.

- 정적 증거: semantic HTML, 링크·문서 lint, 색 토큰, logical property drift
- 렌더 증거: 320/390/768/1280px, 200% 확대, 설치된 서비스워커의 warm-cache,
  느린/실패한 동기화
- 행동 증거: 키보드·터치·날짜 이동·점수 입력·그래프 인출·import/export
- 운영 증거: 변경 slice별 수용 기록, 실제 실패 맥락의 회귀 테스트, 배포 readback

자동 검사는 판정 가능한 부분을 맡고, 브라우저에서만 보이는 읽기·쓰기 감각과 시각적
우선순위는 사람의 확인으로 남긴다.

## 기존 원칙과의 통합

| 기존 불변식·취향 | UI에서의 해석 |
| --- | --- |
| 오프라인이 기본 | 로컬 IndexedDB가 작업 정본이다. 서비스워커가 설치된 뒤 네트워크가 끊겨도 기록·그래프·export가 멈추지 않는다. 최초 cold offline은 별도 계약이다. |
| 동기화는 사람이 누른다 | 자동 pull은 새로고침·복귀 때의 복구일 뿐이고, push는 명령형 버튼으로만 한다. 상태와 미동기화를 보이게 한다. |
| 사용자가 쓴 글자를 잃지 않는다 | import 실패·저장 실패·동기화 분기에서 원문과 conflict 사본을 보존하고 조용히 버리지 않는다. |
| 앱에 LLM을 넣지 않는다 | AI는 검증 가능한 코드·검사·증거 정리에만 관여한다. 기록 내용과 의미는 사람이 쓴다. |
| 기능보다 가능성 | 날짜·블록·점수·그래프·export의 조합으로 인출을 만든다. 새 수단을 먼저 만들지 않는다. |
| 비직교성이 최악 | 점수는 라디오/스트립, 이유는 텍스트, 동기화는 버튼처럼 각 수단의 경계를 유지한다. |
| 적을수록 좋다 | 새 디자인 런타임·차트 의존성·거대한 컴포넌트 체계를 추가하지 않는다. |
| 기록보다 인출 | 그래프와 전날 맥락은 저장 기능이 아니라 이미 쓴 기록을 다시 읽는 통로다. |

## 의도적으로 하지 않는 것

- 이 원칙을 이유로 새 디자인 런타임 프레임워크나 디자인 시스템 의존성을 도입하지 않는다.
- 모든 기기·언어·색·입력 조합을 한 번에 완벽히 지원한다고 주장하지 않는다. 실패하면
  핵심 capability가 사라지는 조합부터 다룬다.
- SSR/no-JS fallback과 최초 방문 cold offline을 현재 UI 패스에 넣지 않는다.
- 폴더·태그·새 taxonomy·앱 내 LLM·AI 생성형 저널·상시 자동 동기화를 추가하지 않는다.
- 색상·타이포그래피·spacing을 전면 교체하지 않는다. 현재의 기록 표면과 되돌릴 수 있는
  작은 slice를 보존한다.

## 이 원칙이 틀릴 수 있는 지점

의도와 맥락을 토큰·검사·런타임 규칙으로 많이 표현하면 오히려 단일 화면을 이해하기
어려워질 수 있다. n=1 앱에서는 해당 조합을 직접 CSS로 고치는 편이 더 싸고 빠를 수도
있다. 따라서 선언을 늘리는 것 자체를 성과로 보지 않고, 실제 예외 override·사용자
혼란·검증 비용이 줄어드는 slice에서만 채택한다.
